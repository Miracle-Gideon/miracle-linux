# Miracle Linux — v0.1 "GhostByte" (proof of concept)

Real Debian running inside PRoot, fully bundled into one Android app,
launched with zero manual setup — no separate Termux install required.

## Build strategy: everything heavy happens on GitHub Actions

All development can happen from Termux + Kali PRoot directly on an Android
device — editing code, git commits, pushing. The actual Android/Gradle
build (which needs a full Android SDK and real compute) runs on GitHub's
servers instead of locally, so no Android Studio, local Gradle, or local
SDK install is ever required.

## The core Android obstacle this project had to solve

Android blocks executing any file an app writes to its own storage at
runtime (a security restriction, confirmed by direct testing — applies
regardless of internal vs external storage, and regardless of `targetSdk`
in some configurations). The only place Android reliably still allows
execution is `nativeLibraryDir` — files the system itself extracts from
the APK's `jniLibs` at install time.

The working solution (verified against Termux's own real, current
architecture, not just theory): every executable and shared library the
rootfs needs is bundled as a fake `.so` file in `jniLibs`, and the real
rootfs paths become **symlinks** pointing into `nativeLibraryDir` at
extraction time. Additionally, Android's restriction affects execution
*through* those symlinks too in some cases — Termux solves this with a
small `LD_PRELOAD` tool called `termux-exec`, which this project also
bundles (`libtermux-exec-ld-preload.so`, copied from a real Termux
install) rather than reimplementing from scratch.

## Preparing the bundled assets

### 1. The rootfs (`app/src/main/assets/rootfs.rootfsblob`)
A minimal, purpose-built Debian rootfs (via `proot-distro install debian`,
never your personal/heavily-customized environment). Named with a
non-standard extension deliberately — Android's build tools automatically
auto-decompress and rename recognized `.gz`/`.tar.gz` assets during
packaging, which silently broke this file the first time around.

### 2. Flattened executables/libraries (`app/src/main/jniLibs/arm64-v8a/*.so`)
Generated by `scripts/flatten_rootfs.py`, which walks the rootfs, finds
every file that's executable or a shared library, copies each into a
flat, jniLibs-safe-named file, and writes a lookup table
(`rootfs_exec_map.tsv`, bundled as an asset) mapping original path →
generated filename. Run with `--strip` to also remove the originals from
the rootfs afterward, since their real bytes now live in `jniLibs` and
keeping both wastes space:

```
python3 scripts/flatten_rootfs.py <rootfs_path> <output_dir> <lookup_table_path> [--strip]
```

### 3. `proot` and its dependencies
Copied from a real, working Termux install (`$PREFIX/bin/proot` →
`libproot.so`), along with its two Termux-specific shared library
dependencies (check with `ldd $PREFIX/bin/proot`) and `termux-exec`
(`$PREFIX/lib/libtermux-exec-ld-preload.so`).

**If your terminal tooling and your project files live in separate apps**
(e.g. native Termux for binaries, a separate proot-based distro for the
actual repo), bridge files between them through shared storage (commonly
`/sdcard/Download`) — they're sandboxed from each other regardless of
both being terminal environments.

## Known limitation in this milestone (by design, not a bug)

`MainActivity.kt` currently pipes bash's stdin/stdout through plain process
streams — not a real pseudo-terminal (pty). Real interactive terminal
behavior (colors, line-editing, ctrl+c, job control) needs native (JNI)
pty allocation — the natural next milestone once bash is confirmed running.

## The one test that matters for this milestone

Open the app → real `bash` prompt output appears → type `ls` → real Debian
filesystem output comes back. Everything else (desktop UI, theming, bridge
commands) builds on top of this once it's proven solid.
